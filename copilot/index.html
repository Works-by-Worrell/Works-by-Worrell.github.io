OPERATIONAL STANDARD // THE CORE LOOP

Context → Intent → Change → Proof

The four-stage loop for reliable engineering outcomes across any tool.

01
CONTEXT
  • • Provide specific files: symbol names, error messages, and command outputs.
  • • State environment constraints: runtime versions, libraries, and protocols.
Never assume the model knows which slice of the system matters.
02
INTENT
  • • Declare desired behavior: state what success looks like explicitly.
  • • Establish boundaries: say what may change, what must NOT change, and edit rights.
Say what you mean—and what you do NOT mean.
03
CHANGE
  • • Ask for one focused edit: keep diffs small, isolated, and readable.
  • • Enforce existing patterns: reuse existing domain helpers and error handling.
Broad prompts produce broad, unreviewable diffs.
04
PROOF
  • • Inspect the diff: verify every added or removed line manually.
  • • Run the checks: execute the smallest relevant unit test, build, or linter.
Fluency is not proof. Automated checks establish trust.
ENGINEERING REALITY This is not bureaucracy added around AI. It is the normal engineering discipline made explicit enough for an assistant to follow.
PROMPT BOUNDARIES // NEGATIVE CONSTRAINTS

Say What You Mean—And What You Do Not Mean

Boundary language protects your worktree from silent refactoring and scope creep.

copilot-cli — prompt-with-boundaries
$ gh copilot suggest \
"Explain how this request flows through the repository.
Identify the relevant files and tests.
Do not edit anything yet."
JOB: Flow Trace SCOPE: Files & Tests BOUNDARY: No Edits
Notice: The prompt assigns a job, a concrete scope, an expected deliverable, and an absolute permission boundary. It explores without touching a single file.
“Explain this; do not edit files.”
Zero-mutation guarantee. Allows safe exploration of critical production code.
“Change only this behavior; do not refactor unrelated code.”
Blast-radius containment. Stops the model from reformatting or reorganizing imports.
“Preserve the public API and existing error handling.”
Interface contract lock. Prevents subtle breaking changes across caller services.
“List assumptions and open questions before implementing.”
Pre-flight alignment. Surfaces misunderstandings before lines of code are written.
“Run the smallest relevant check and report what it verified.”
Accountable validation. Forces focus on the proof criteria rather than speculative claims.

RISK MITIGATION // NON-NEGOTIABLE GUARDRAILS

Fluent Does Not Mean Correct

Guardrails we do not outsource. Fluency is not proof.

Verify APIs & Types 01

Models invent non-existent method signatures and parameters with complete syntactic confidence. Always verify against the actual source.

Keep Diffs Reviewable 02

Broad prompts produce sprawling diffs. If you cannot understand every changed line in 3 minutes, reject it and narrow the scope.

Zero Secrets In Prompts 03

Never paste API tokens, private keys, connection strings, customer PII, or unreleased proprietary specs into prompts.

Review Terminal Commands 04

Never blind-execute generated shell commands—especially operations involving rm, git reset, drop tables, or migrations.

Retain Architecture Rights 05

Do not let Copilot silently decide system architecture, security boundaries, or business domain rules. Those need accountable human ownership.

Check For Silent Failures 06

Watch for swallowed exceptions, empty catch blocks, fake mocks, and removed assertions generated just to make tests green.

🚨 The Golden Rule of Engineering Ownership: The model has no skin in the game. When a production incident fires at 02:00, the engineer answers the pager.
LIVE WORKFLOW // METHODOLOGY OVER LATENCY

A Small Demo Beats A Giant Repository Tour

Applying the 4-step loop to a bounded slice of the repository live.

STEP 1 ORIENT
Explore (No Edits)
“Give me a concise map of this repo for a new engineer. Main services, entry points, tests. Cite files. Do not edit anything.”
Discipline: Request citations; explicitly prohibit edits; build mental model first.
STEP 2 TARGET
Target Narrow Gap
“Based on that map, find one documentation gap that can be fixed without changing code. Propose smallest change. Do not edit until approved.”
Discipline: Decouple proposal from execution; hold the human approval gate.
STEP 3 MUTATE
Make Approved Edit
“Make only the approved documentation change. Preserve existing style. Do not touch source code or dependencies. Show concise diff.”
Discipline: Inspect git diff live: Did it touch only the approved file? Did it invent paths?
STEP 4 VALIDATE
Prove The Result
“Verify this documentation change using the smallest check. Inspect for broken Markdown and invalid paths. Report what you verified.”
Discipline: Validate claims with concrete checks before committing to the branch.
💡 Key Takeaway: The value of the demo is the method, not model latency. Bounded requests produce reviewable outcomes.

FINAL SYNTHESIS // OPERATIONAL HABIT

Keep The Power. Supply The Context.

Four non-negotiable principles for engineering leverage.

01
Start small.
Focus on one class, one isolated script, or one bounded CLI query. Avoid sprawling repository scans.
02
State the boundaries.
Say what may change, what must NOT change, and editing permissions. Negative constraints preserve sanity.
03
Review the result.
Line-by-line diff inspection. If you cannot explain every changed token, do not commit it.
04
Run the checks.
The compiler, linter, and unit test suite are the ultimate arbiters of truth. Trust is earned through execution.
“Copilot is an engineer’s second set of eyes across a complicated system. It is not the person responsible for the result.”
